تحديث 27 أكتوبر: بلاغ جديد من غير تقييم للجوع أو الطاقة لا يمسح آخر تقييم صريح حديث. كل درجة تحتفظ بتاريخها وصلاحيتها الأصلية، والتحديث الصريح يغيّر الدرجة التي ذكرها المستخدم فقط. رسالة الجوع تشير لتاريخ رصده الحقيقي. الإصلاح اختُبر في منع اقتراح وقبول خفض السعرات بعد بلاغ ناقص، ثم السماح بالمراجعة بعد تحسن صريح في الدرجتين. نجح الاختبار الشامل بـ298 اختبارًا، ومسار HTTP من 52 طلبًا و10 تحققات، واختبار واجهة المتابعة على عرضين. تفاصيل النشر والنسخة الاحتياطية في [تقرير الإصلاح](production-readiness/FEEDBACK_MEMORY_REPAIR.md).

## السلوك المنفذ

- أسباب تعثر منظمة للتغذية (وقت، تكلفة، طعم، جوع، أكل خارج البيت، تسجيل) والتمرين (وقت، تعب، ألم، معدات، دافعية)، مع خيار عدم وجود عائق.
- تسجيل اختياري للجوع والشبع والطاقة من 1 إلى 5. التاريخ والمنطقة الزمنية يحددهما الخادم، ولا نقبل درجات خارج النطاق أو تحويل نص إلى رقم.
- لكل خطوة: الدليل، الخطة التي تخصها، حالة الاقتراح، قبول/رفض المستخدم، موعد مراجعة، ونتيجة يبلّغ عنها المستخدم. قبول الخطوة السلوكية لا يُغير خطة الغذاء أو التمرين؛ تعديل الخطة ما زال يمر بمسار adaptation المحمي.
- تكرار نفس البلاغ لا ينشئ اتفاقًا نشطًا ثانيًا. الاقتراح غير المقبول ينتهي بعد سبعة أيام، ويتجدد ببلاغ جديد. تغير الخطة يُنهي صلاحية الاتفاق المرتبط بها دون حذف تاريخه.
- نتيجة «لم تساعد» أو «لم أجرب» تفتح سؤالًا عن العائق الحالي بدل إعلان نجاح أو تكرار نفس النصيحة تلقائيًا.
- الجلستان المسجلتان صراحة كفائتتين أو يومان مكتملان مختلفان عن هدف الأكل يفتحان سؤالًا عن السبب. غياب التسجيل وحده لا يُصنف فشلًا في الالتزام.
- الجوع المرتفع أو الطاقة المنخفضة في بلاغ التغذية الحديث يمنعان اقتراح/قبول خفض السعرات. هذا حاجز محافظ بالمنتج، وليس تشخيصًا أو معايرة طبية للاحتياج.
- الألم المبلغ عنه عبر العوائق يمنع التدرج حتى متابعة صحية لاحقة؛ لا يكفي اختيار «مفيش عائق» أو انتظار مرور الوقت أو تغيير الخطة لإلغاء هذه الإشارة.
- تسجيل الأدلة المهمة عبر API يشغّل مراجعة في نفس عملية الحفظ: الاستشفاء، الوزن، الأكل، إكمال/حذف التسجيل، الجلسة، التمرين، العائق، تجديد الخطة، المنطقة الزمنية وتأكيدات الجاهزية. لا يُطبق تعديل السعرات أو الجولات بدون الموافقة المطلوبة أصلًا.
- تسجيل الماء/النشاط وتفضيلات الإشعارات والإقرار بالرسالة لا يُلغي اقتراحًا صالحًا غير متعلق بهذه البيانات؛ يُحدّث رقم مراجعته مع بقاء تاريخ صلاحيته.
- رسائل المتابعة تعطي أولوية للسلامة ثم الاتفاقات المستحقة. ملاحظات التغذية تبرز انتهاء الخطة والجوع المرتفع واتجاه الوزن بدل اختيار الموضوع لمجرد تنويع النص.
- أُزيل ادعاء أن حجم التمرين مثالي أو يحقق تقدمًا مثبتًا عندما تكون النتيجة الحقيقية «لا يوجد دليل كافٍ لزيادة المجموعات».

## API للموبايل

كل تعديل يستخدم `POST /v1/commands` مع `revision` و`Idempotency-Key`، ويدعم `Prefer: return=minimal`. إعادة الطلب بنفس المفتاح لا تكرر القرار. تعارض مراجعة الحساب يعيد 409 كالمعتاد.

| action | payload |
|---|---|
| coaching_feedback | domain: nutrition/training، barrier من القائمة المسموحة، hunger/satiety/energy اختيارية |
| coaching_decision | id، accept: boolean |
| coaching_outcome | id، outcome: helped/not_helped/not_tried |
| coaching_ack | id؛ يُرسل بعد إقرار صريح من العميل ولا يُستنتج من GET |

`GET /v1/coaching/inbox` يعرض المتابعات النشطة و`reviewDue` و`expired` وفق تاريخ المستخدم. `GET /v1/coaching/history` يستخدم from/to/offset/limit ويعيد nextOffset؛ أعد بدء الصفحات عند حدوث تغييرات أثناء القراءة. `GET /v1/coaching/brief` يربط الملاحظة المهمة بـ`caseId` عند وجود متابعة مناسبة.

حالات الاتفاق: question → proposed (عن طريق بلاغ جديد يحفظ السؤال السابق superseded) → accepted/declined → completed. تغير السياق يمكن أن يحول الحالة إلى superseded. `reviewOn` تاريخ محلي؛ `createdAt` وبقية الطوابع الزمنية UTC. نتيجة helped لا تُقبل قبل موعد المراجعة، والنتائج الثلاث تُخزن كـuser_report ولا تثبت سببية أو فاعلية علاجية.

قراءة inbox أو brief لا تغير revision ولا تثبت أن المستخدم قرأ الرسالة. `deliveryStatus: NOT_SENT` و`pushConfigured: false` متعمدان؛ الشاشة المفتوحة ليست دليل تسليم Push. العروض داخل التطبيق عند الطلب لا تُحجب بسبب ساعات هدوء الإشعارات.

## التخزين والمزامنة

ترحيل `0004_coaching_journey.sql` يضيف `coaching_cases` و`coaching_feedback` بمفاتيح مركبة تشمل هوية المالك. تُحفظ التغييرات مع الحساب وإيصال العملية وoutbox في نفس دفعة D1 المحمية بالمراجعة ورمز محاولة الحفظ.

تُقرأ بيانات المتابعة مع snapshot الحساب في المعاملة نفسها. عند وجود الجداول تخرج هذه السجلات من JSON الحساب ويُحفظ تاريخها في الجداول. الترقية من حساب يستخدم التخزين القديم تنقل السجلات في أول حفظ دون إسقاطها. نقل الحساب المجهول ينقلها ويزيل المصدر؛ الحذف الكامل يمسحها والتصدير يشملها.

أسماء sync الجديدة: `coaching_case` و`coaching_feedback`. العميل يخزنها حسب entityId ويستكمل الصفحة باستخدام afterSeq/nextSeqCursor. لا يجوز اعتبار الرد المعاد للعملية تغييرًا جديدًا.

التخزين المنظم هنا لا يحل وحده تكلفة تحميل التاريخ الكامل أو حدود JSON لبقية أنواع البيانات. هذه حدود إنتاجية ما زالت تحتاج معالجة وقياس حمل.

## التحقق وحدود الإصدار

الاختبارات الجديدة تغطي حالات الاتفاق والرفض والصلاحية والسياق والألم والجوع، واستمرار الاقتراح بعد تسجيل الماء والإقرار، والتخزين والعزل وإعادة الطلب والمزامنة والحذف، وتجربة ويب على شاشتي 390 و1280 بكسل. الفحوص العامة تشمل البناء والبيانات واختبارات المشروع والمتصفح. التحقق المحلي: 291 اختبارًا ضمن npm run check، واختبار إضافي مستقل للترقية ونقل الحساب نجح (الإجمالي الحالي 292)، وكل رحلات المتصفح نجحت بما فيها محاكاة 15 يومًا. npm audit أعاد صفر ثغرات معروفة. حزمة Worker اجتازت dry-run دون نشر. راجع CI الخاص بالـcommit المنشور للتحقق من التنفيذ الموحد.

المتبقي الذي لا يُدّعى إنجازه:

- جدولة وإرسال Push في الخلفية مع مزود فعلي وإيصالات تسليم، وضبط تكرار الإرسال وساعات الهدوء وإعادة المحاولة. موعد المتابعة الحالي يظهر عند فتح التطبيق؛ لا يوجد Cron يدّعي أنه تواصل مع مستخدم غائب.
- اختيار وربط مزود هوية وتجديد جلساته؛ واجهة تسجيل الدخول تظل مؤجلة حسب طلب المستخدم السابق.
- بناء واختبار عميل KMM على أجهزة حقيقية، والطابور المحلي دون إنترنت.
- تشغيل المراقبة والاستعادة والحدود الموزعة على بيئة الإنتاج.
- توثيق وصفات محلية موزونة ومراجعة مختصين للقرارات، وتطوير مراحل تدريب طويلة المدى. لم نضف توصيات علاجية أو أرقامًا غذائية غير موثقة لتعويض هذه الأعمال.

النشر يكون على Worker وD1 الحاليين فقط. يلزم نسخة احتياطية قابلة للاستعادة وتطبيق الترحيل قبل النشر، ثم فحوص على النشر الحي. في جلسة التنفيذ الحالية أكد Wrangler عدم وجود تسجيل دخول Cloudflare؛ لم ننشر على استضافة بديلة ولم نُجر ترحيلًا بعيدًا.
