# مراجعة النضج ومحاكاة رحلة المستخدم — 0.10

نقطة المقارنة: `bb9cc3abedf4840547e5ae36c43675a0b9955da2`، إصدار0.9. تاريخ العمل:23 أكتوبر2026. هذه المراجعة تقارن متطلبات المحادثة ووثائق المشروع بالتنفيذ؛ لا توجد داخل المستودع مواصفة مستقلة تثبت قائمة مغلقة لكل ما قد يعنيه «أقصى طاقة للمحركين».

## الحكم الفعلي

يوجد MVP قابل لتجربة مسارات التغذية والتمرين والاستشفاء والتكيف، وتحسن التعامل مع الحالات الطرفية. **لا يوجد دليل يبرر وصفه بأنه يغطي كل السيناريوهات، أو أنه منتج ناضج لا يحتاج شيئًا آخر.** وجود868 تمرينًا ونجاح الاختبارات لا يثبت جودة كل وصفة تدريبية أو غذائية لكل مستخدم، ولا يعوض مراجعة المختصين وتجارب مستخدمين حقيقية.

المحاكاة الجديدة تسمح باختبار رحلة متعددة الأيام باستخدام نفس المحركات والتخزين والقرارات، فتجعل تقييم المتابعة عمليًا بدل الاكتفاء بمشاهدة خطة اليوم الأول. بياناتها تظل افتراضية ومعزولة، ونجاحها ليس دراسة نتائج بشرية.

## ما كشفته المراجعة الثانية وأصلحته

أُنشئت6 اختبارات جديدة وفشلت جميعها على0.9 قبل الإصلاح. اختبارات MAT في `tests/maturity.test.mjs` تغطي:

1. الألم المسجل أثناء تمرين بعد متابعة سليمة كان لا يغير تقييم الاستشفاء العام. الآن يوقف التقدم لحين إعادة التقييم؛ تعديل سجل ألم قديم ليس تقرير ألم جديدًا تلقائيًا.
2. تخفيف20% مع مجموعتين كان يُقرب إلى مجموعتين، فلا يحدث تخفيف. الآن تنخفض الوصفة متعددة المجموعات مجموعة واحدة على الأقل؛ الحد الأدنى مجموعة، والنسبة الفعلية تتأثر بالتقريب الصحيح.
3. تغيير الهدف كان قد يعيد استخدام اتجاه الوزن والأكل السابقين فورًا. الآن يبدأ سياق أدلة جديد، وتبقى السجلات القديمة محفوظة؛ تجديد الأسبوع لا يمسح سياق الهدف.
4. الحفاظ على الوزن كان يتجاهل الانحراف المستمر رغم كفاية البيانات. الآن يستخدم اقتراحًا محدودًا عند تجاوز±0.5% أسبوعيًا؛ هذه عتبة منتج وليست معيارًا طبيًا شاملًا.
5. واجهة يوم الأكل كانت تعرض إجمالي السجل القديم بينما endpoint اليوم يعيد قيمًا مجهولة. أصبح العقد متسقًا مع القيم المعروفة، وتبقى المغذيات غير المعروفة null.
6. قيمة نصية بدل boolean لاكتمال اليوم كانت تتحول بصمت. أصبحت مرفوضة.

كما أصبحت البيانات الجديدة تلغي عرض المراجعة السابقة وتُبطل اقتراحاتها المعلقة. وكشف اختبار D1 أن كاتبين متزامنين بنفس جسم الحساب تمامًا قد يسجلان إيصالين رغم فوز تحديث واحد؛ أُضيف رمز داخلي فريد لكل محاولة داخل شرط المعاملة، وأصبح الاختبار يثبت إيصالًا واحدًا فقط. هذا الرمز لا يصل للعميل ولا يغيّر الهوية.

## استخدام المحاكاة

1. افتح «خطتي» ثم «افتح وضع المحاكاة».
2. اختر نسخ بياناتك الحالية المؤكدة، أو الشخصية الجاهزة: بالغ30 سنة،80 كجم، هدف خسارة تدريجية،3 أيام تمرين أسبوعيًا. يمكنك تعديل شخصية المحاكاة عبر نفس الأونبوردينج.
3. سجّل أكلك وتمرينك واستشفاءك ووزنك يدويًا. البطاقات توضح ما سُجل وما بقي، واليوم الذي لا يحتوي جلسة يظهر كراحة من المقاومة.
4. اضغط «راجع يومي» لترى سبب الاحتفاظ بالخطة أو الاقتراح وشروطه. قبول الاقتراح مستقل عن تقديم اليوم.
5. اضغط «انتقل لليوم التالي». يتغير تاريخ الباك إند والتسجيل والتقويم وحداثة الاستشفاء ونوافذ المراجعة، ويُحفظ ملخص اليوم السابق. يتجدد أسبوع الأكل بعد انتهاء مدته بنفس القيود؛ فشل التوليد يُعرض دون اختلاق خطة.
6. يمكنك إغلاق الموقع والعودة لاستكمال الجولة، أو الرجوع للحساب الفعلي، أو بدء جولة جديدة. إعادة الجولة تصفّر الحالة الظاهرة وسجلاتها، لكنها لا تعد بمسح أرشيف الجولات الداخلي من قاعدة البيانات.

التعبئة السريعة اختيارية لليوم الفارغ فقط، وترفض الاستبدال إذا كنت سجلت أي بيانات. السيناريوهات: التزام مع تغير تدريجي للوزن، ثبات وزن، نوم قليل وإجهاد، تفويت تمرين، أكل أقل من الخطة، أو ألم. كل القيم المعبأة افتراضية، والقرار ينتج من القواعد نفسها وليس نصًا جاهزًا خاصًا بالسيناريو. في ضعف الاستشفاء لا تُملأ جلسة مكتملة؛ وفي الألم تُسجل جلسة جزئية عند وجود تمرين لذلك اليوم.

## كيف يتحقق العزل

الـAPI يقبل `simulation=1` ويشتق مفتاح مساحة تجربة من هوية الاستضافة الحالية. الحساب الفعلي وأرشيفاته وإيصالاته لا تُكتب أثناء التجربة، ولا يختار العميل هوية مستخدم آخر. نفس معرف خطة الحساب الفعلي لا يمكن قراءته من مساحة المحاكاة والعكس. لا توجد عملية ترحيل تلقائي لبيانات المحاكاة إلى الحساب الفعلي.

الزمن محلي للطلب باستخدام AsyncLocalStorage، وليس تعديلًا عامًا لـDate أو متغيرًا مشتركًا بين المستخدمين. تاريخ البداية هو تاريخ القاهرة الفعلي وقت إنشاء الجولة، وبعده يقدم الزر الزمن يومًا واحدًا. تستخدم الواجهة `serverDate/serverNow` بدل افتراض أن ساعة الجهاز هي ساعة التجربة. طوابع سجلات المجال والخطط افتراضية؛ طوابع إيصالات التخزين والمزامنة تحتفظ بوقت التشغيل الفعلي.

كل انتقال أو تعبئة يخضعان لرقم المراجعة ومنع تكرار الطلب. إعادة إرسال طلب «اليوم التالي» بنفس المفتاح لا تقدم يومًا ثانيًا. التجربة لا تسجل الطعام أو التمرين أو الوزن تلقائيًا لمجرد تقديم اليوم؛ اليوم الناقص يظل ناقصًا.

## أدلة التحقق وحدودها

- نجح البناء و100 اختبار وحدة/مجال/HTTP/D1، بما فيها subtests؛ ليست100 رحلة بشرية مختلفة.
- اختبرت رحلة15 يومًا بنفس المحركات: تجميع الأدلة، وتجديد الأسبوع، وثبات الوزن، واقتراح سعرات، واعتماده، وسريانه من اليوم التالي.
- اختُبر تزامن ساعتين افتراضيتين مع الساعة الفعلية، وعزل حسابين وأرشيفاتهما، وحفظ الجولة وإعادة الطلب ونسخ التفضيلات دون السجلات، ورفض التواريخ المستقبلية خارج يوم كل مساحة.
- اختُبرت الأيام الناقصة، رفض الكتابة التجريبية فوق اليدوية، الألم وضعف الاستشفاء، بدء جولة جديدة وحد90 يومًا، وحدود المعاملة عندما يتطابق جسم تحديثين متزامنين.
- اختبارات المتصفح تشمل الرحلات الأصلية والموبايل والديسكتوب وسباقات الشبكة، مع رحلة المحاكاة اليومية والتعبئة والمراجعة والاعتماد والعودة للحساب الفعلي والاستكمال وإعادة الجولة.
- مصفوفة0.9 المسجلة تظل دليلًا على2,250 تركيبة تمرين و333 محاولة غذاء بالشروط المحددة هناك. لم تتحول إلى اختبار لكل القياسات والأعمار والاستبعادات الممكنة؛ معظم عيناتها الغذائية تستخدم قياسات جسم ثابتة.

أوامر إعادة التحقق: `npm run check` ثم `npm run dev`، وفي طرفية أخرى `npm run test:browser`. الاختبارات الجديدة: `tests/maturity.test.mjs` و`tests/simulation.test.mjs` و`tests/api-simulation.test.mjs` و`scripts/browser-simulation.mjs`.

## ما يلزم قبل ادعاء النضج الكامل

الأولوية التالية هي تقييم خبراء تغذية وتدريب لخطط مستخدمين مختلفين، وقياس واقعية الحصص والتنوع والقيود وجودة تغطية الحركات، ثم تجربة طولية مع مستخدمين حقيقيين. هذه الأدلة لم تُجرَ ولا يمكن استبدالها بعدد اختبارات برمجية.

تشغيليًا: ما زال التخزين بتجميع سجل محدود1.5MB للحساب، والطلبات40KB، وتاريخ القاهرة للجميع. يلزم تقسيم سجلات المتابعة وصفحاتها، واختبار حمل واسترجاع ونسخ احتياطي موثق، ومراقبة تشغيلية وحدود طلبات، ومنطقة زمنية لكل مستخدم. يلزم تصميم المتابعة المجدولة والإشعارات، ثم هوية KMM والمزامنة حسب قرار إطلاق التطبيق؛ الدخول ما زال مؤجلًا كما طُلب.

التسليم الحالي هو تجربة تفاعلية أقوى وقابلة للمراجعة، مع إصلاح الحالات المثبتة وتوثيق الفجوات. لا يوجد أساس صادق لقول «كل السيناريوهات مغطاة» أو «النظام مش محتاج أي حاجة تانية».
